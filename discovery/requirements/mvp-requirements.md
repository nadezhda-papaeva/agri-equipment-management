# Требования к MVP системы учёта сельскохозяйственной техники

## 1. Контекст

По результатам обследования сельскохозяйственного предприятия были выявлены проблемы, связанные с ручным контролем обслуживания техники, отсутствием единой базы запасных частей и поставщиков, а также рисками простоев при внеплановых поломках.

В качестве аналитической рекомендации предложена концепция решения на базе low-code инструмента AppSheet и электронных таблиц.

Документ содержит **предлагаемые требования к MVP**. Их реализация и окончательный состав подлежат согласованию с заказчиком.

## 2. Цель MVP

Обеспечить централизованный учёт сельскохозяйственной и транспортной техники, запасных частей и сроков обслуживания для снижения зависимости от ручного контроля и своевременного планирования закупок.

## 3. Пользователи

**Основной пользователь:** управляющий предприятием.

Возможность расширения доступа для водителей и других сотрудников рассматривается на последующих этапах.

## 4. Бизнес-требования

| ID | Требование |
|---|---|
| BR-01 | Снизить риск простоя техники из-за несвоевременного обслуживания и отсутствия запасных частей. |
| BR-02 | Сократить время поиска информации о технике, деталях и поставщиках. |
| BR-03 | Повысить прозрачность планирования закупок и регламентных работ. |
| BR-04 | Минимизировать затраты на внедрение и сопровождение решения. |

## 5. Функциональные требования

| ID | Требование |
|---|---|
| FR-01 | Пользователь должен иметь возможность просматривать единый реестр техники. |
| FR-02 | Для каждой единицы техники должна быть доступна карточка с наименованием, типом, регистрационным или инвентарным номером, ответственным сотрудником и статусом. |
| FR-03 | Пользователь должен иметь возможность добавлять и редактировать сведения о технике. |
| FR-04 | В карточке техники должен отображаться перечень контролируемых запасных частей и расходных материалов. |
| FR-05 | Для каждой контролируемой детали должны фиксироваться дата последней замены, период эксплуатации и плановая дата следующей замены. |
| FR-06 | Система должна рассчитывать плановую дату следующей замены на основании введённых данных. |
| FR-07 | Система должна визуально выделять детали за 30, 14 и 7 дней до плановой замены. |
| FR-08 | Пользователь должен иметь возможность учитывать текущий и минимальный остаток запасных частей. |
| FR-09 | Система должна позволять получать список деталей, требующих закупки, на основании сроков замены и складских остатков. |
| FR-10 | Пользователь должен иметь возможность просматривать и редактировать базу поставщиков с контактами, примерными ценами и сроками доставки. |
| FR-11 | Для критичных деталей должна быть предусмотрена возможность указания приоритета. |

## 6. Нефункциональные требования — предложения для согласования

| ID | Требование |
|---|---|
| NFR-01 | Интерфейс должен быть простым и понятным пользователю без специальной технической подготовки. |
| NFR-02 | Решение должно быть доступно с мобильного устройства. |
| NFR-03 | Доступ к изменению данных должен предоставляться только авторизованным пользователям. |
| NFR-04 | Решение должно допускать последующее расширение перечня техники, запасных частей и поставщиков без полной переработки структуры. |
| NFR-05 | При выборе способа реализации необходимо учитывать стоимость внедрения и сопровождения. |

Количественные критерии производительности, доступности и объёма данных требуют дополнительного уточнения с заказчиком.

## 7. Предварительные критерии приёмки MVP

1. Пользователь может добавить единицу техники и открыть её карточку.
2. Для техники можно зафиксировать перечень контролируемых деталей.
3. После ввода исходных данных определяется следующая плановая дата замены.
4. При приближении даты замены деталь выделяется в соответствии с установленными интервалами.
5. Пользователь видит текущие и минимальные остатки деталей.
6. Можно сформировать перечень деталей, требующих закупки.
7. Для детали можно найти информацию о возможных поставщиках.

## 8. Функциональность следующих этапов

В рамках дальнейшего развития предлагается рассмотреть:

- цифровой журнал ежедневных проверок техники;
- расширенное планирование работ на основе статуса техники;
- автоматическую интеграцию с погодными данными;
- формирование рекомендаций по выпуску техники на сенокос;
- управленческую аналитику и дашборды;
- дополнительные механизмы уведомлений.

## 9. Статус документа

Требования сформированы в рамках аналитической проработки целевого решения на основании выявленных проблем AS-IS.

Документ представляет собой предложение по составу MVP, а не описание уже реализованного функционала.
