# Анализ вариантов реализации системы учета и обслуживания сельскохозяйственной техники

## 1. Цель анализа

По результатам обследования бизнес-процессов была выявлена потребность в более системном учёте сельскохозяйственной техники, контроле сроков замены деталей, управлении запасами запчастей и хранении информации о поставщиках.

Цель анализа — сравнить возможные варианты реализации предлагаемого решения и определить подход, наиболее подходящий для создания MVP с учетом текущего масштаба предприятия и выявленных требований.

Рассматриваемое решение является аналитической рекомендацией. Выбор конкретной платформы и окончательный состав функциональности требуют дополнительного согласования с заказчиком.

## 2. Основные требования к решению

При сравнении вариантов учитывались следующие требования:

- ведение единого реестра техники;
- хранение карточек техники и контролируемых деталей;
- фиксация дат последней и плановой замены деталей;
- контроль сроков планового обслуживания;
- контроль текущих и минимальных остатков запчастей;
- формирование информации о необходимости закупки;
- ведение базы поставщиков;
- возможность использования на мобильных устройствах;
- простой интерфейс для пользователей с различным уровнем цифровой грамотности;
- возможность развития функциональности без полной переработки системы;
- ограниченные затраты на создание и сопровождение MVP.

- ## 3. Варианты реализации

### Вариант 1. Excel / Google Sheets

Наиболее простой вариант предполагает развитие существующего подхода на основе электронных таблиц.

В таблицах могут храниться:
- перечень техники;
- данные о деталях;
- даты плановых замен;
- остатки запчастей;
- поставщики и их предложения.

Для контроля сроков возможно использование формул, условного форматирования и дополнительных таблиц.

#### Преимущества

- минимальные первоначальные затраты;
- знакомый пользователям интерфейс;
- быстрый запуск;
- возможность самостоятельно изменять структуру таблиц.

#### Ограничения

- увеличение количества связанных таблиц усложняет работу пользователей;
- высокий риск ручных ошибок;
- сложнее обеспечить единообразие данных;
- ограниченные возможности построения пользовательских сценариев;
- при росте количества техники и записей повышается сложность сопровождения;
- автоматизация уведомлений, закупок и истории обслуживания требует дополнительных настроек.

Таким образом, электронные таблицы могут использоваться как временное решение, однако при расширении процессов их возможностей может быть недостаточно.
### Вариант 2. Low-code приложение на базе AppSheet

Второй вариант предполагает создание приложения на low-code платформе AppSheet.

В качестве источника данных могут использоваться структурированные таблицы, при этом пользователи работают с ними через отдельный интерфейс приложения.

В рамках MVP могут быть реализованы:
- реестр техники;
- карточки техники;
- перечень контролируемых деталей;
- учет остатков;
- плановые даты замены;
- список деталей, требующих внимания;
- база поставщиков;
- фиксация ремонтов и замен;
- формы для ввода и обновления информации.

#### Преимущества

- сравнительно высокая скорость создания MVP;
- отсутствие необходимости полноценной программной разработки;
- возможность использования приложения на мобильных устройствах;
- создание отдельных форм и представлений для разных бизнес-сценариев;
- возможность автоматизации части проверок и уведомлений;
- возможность постепенно расширять функциональность.

#### Ограничения

- зависимость от возможностей выбранной low-code платформы;
- необходимость корректной настройки структуры данных и прав доступа;
- возможные ограничения при дальнейшем значительном масштабировании;
- часть сложной бизнес-логики может потребовать дополнительной настройки или перехода на другое технологическое решение.

Для рассматриваемого масштаба предприятия данный вариант позволяет проверить предлагаемую модель процессов без значительных затрат на полноценную разработку.
### Вариант 3. Готовая CRM / ERP-система

Третий вариант предполагает использование существующей корпоративной информационной системы с последующей настройкой под процессы предприятия.

Потенциально такая система может объединять учет техники, закупки, поставщиков, финансовые операции и другие процессы предприятия.

#### Преимущества

- широкие функциональные возможности;
- возможность дальнейшего масштабирования;
- наличие инструментов разграничения доступа;
- возможность объединения нескольких процессов предприятия в одной системе;
- развитые возможности отчетности и интеграций.

#### Ограничения

- более высокая стоимость внедрения и сопровождения;
- более длительный срок настройки;
- часть функциональности может быть избыточной для текущего масштаба предприятия;
- требуется обучение пользователей;
- бизнес-процессы предприятия могут потребовать дополнительной адаптации системы.

На этапе MVP внедрение комплексной CRM или ERP-системы может оказаться несоразмерным текущему объему задачи.### Вариант 4. Разработка собственного приложения

Четвертый вариант предполагает разработку отдельной информационной системы специально под требования предприятия.

Система может быть спроектирована с учетом всех выявленных процессов и потенциальных интеграций.

#### Преимущества

- возможность максимально точно учитывать бизнес-требования;
- отсутствие функциональных ограничений, характерных для готовых платформ;
- возможность проектирования архитектуры с учетом дальнейшего масштабирования;
- полный контроль над развитием системы.

#### Ограничения

- наиболее высокая стоимость среди рассматриваемых вариантов;
- длительный срок разработки;
- необходимость привлечения разработчиков, тестировщиков и специалистов по сопровождению;
- дополнительные затраты на инфраструктуру и поддержку;
- повышенные риски для MVP из-за большого объема первоначальных инвестиций.

Для проверки аналитических гипотез и базовой функциональности данный вариант представляется избыточным.

## 5. Рекомендуемый вариант

Для реализации MVP предлагается рассмотреть low-code подход на базе AppSheet.

Выбор обусловлен тем, что на текущем этапе требуется не создание крупной корпоративной информационной системы, а проверка предложенной модели работы и автоматизация наиболее проблемных процессов:

- учета техники;
- контроля сроков замены деталей;
- контроля запасов;
- подготовки информации для закупки;
- хранения данных о поставщиках;
- ведения истории ремонтов и замен.

Low-code подход позволяет создать рабочий прототип системы без полноценного цикла программной разработки и проверить удобство предложенных процессов на практике.

При успешной апробации MVP возможны два дальнейших сценария:

1. развитие приложения и постепенное добавление новых функций;
2. использование результатов MVP и накопленных требований как основы для выбора или разработки более масштабной информационной системы.

Таким образом, AppSheet рассматривается не как окончательная архитектура системы, а как возможный инструмент для быстрой проверки предлагаемого решения.

## 6. Риски и ограничения рекомендуемого варианта

При выборе low-code платформы необходимо учитывать следующие риски:

- зависимость от возможностей и ограничений платформы;
- необходимость предварительной проверки сценариев работы при нестабильном или отсутствующем интернет-соединении;
- необходимость контроля корректности синхронизации данных;
- возможное усложнение приложения при значительном расширении количества процессов;
- зависимость стоимости использования от количества пользователей и условий лицензирования;
- необходимость пересмотра технологического решения при значительном масштабировании бизнеса.

До начала реализации MVP рекомендуется отдельно проверить критичные сценарии работы, включая мобильное использование, синхронизацию данных и работу пользователей в условиях нестабильного интернет-соединения.

## 7. Итог

По результатам анализа наиболее подходящим вариантом для проверки предлагаемого решения является создание MVP с использованием low-code платформы.

Данный подход обеспечивает баланс между скоростью реализации, стоимостью, удобством для пользователей и возможностью автоматизировать ключевые процессы.

Рекомендация сформирована на основании результатов обследования предприятия и требований к предполагаемому MVP. Фактический выбор платформы должен осуществляться после технической проверки критичных сценариев и согласования с заказчиком.
